# mode-propose

将探索结论写成**可被另一会话直接落实**的方案。设计阶段把分叉抛给用户拍板；拍板前不要假装合同已闭合。

允许修改的范围：`agents/proposes/` 内。禁止改工程目录（`lib/`、`test/`、`README.md`、`agents/fixed_list.md` 等）。

## 目录合同

每个方案一个目录，固定两个文件：

```
agents/proposes/<name>/
  schemes.md    # 建设性合同：目标、方案、已决、关注点、未决
  tasks.md      # 执行合同：按大步骤分组的勾选列表
```

`<name>`：小写 + 下划线；**首词必须是动词**（`add`、`fix`、`update`、`remove`、`rename`、`move` 等）。

拆文件是为了让建设性文字不必再压成一句话，同时让落实 Agent 按需读：先读 `schemes.md` 的已决与关注点，再按 `tasks.md` 执行。不要把实现代码写进任一文件。

遗留的单文件 `agents/proposes/<name>.md` 仅兼容读取；**新建或修订时改为目录格式**（把旧文拆进上述两文件后删除该 `.md`）。

## 工作步骤

### 1. 收集上下文

- 整理 explore 结论、用户意图、真实路径与符号；缺口用 `Read` / `Grep` / `Glob` 补全
- 若从 **mode-patch** 打回：把已发现的分叉或架构面写入合同，按标准流程补全，不要再推回 patch
- 函数名、路径不要臆造；读不到则先问用户
- 修订已有方案时：以 `schemes.md` 的「目标」为准，只补合同缺口

### 2. 先抛分叉，再写任务

落实时才发现的选择，是设计阶段的失败。在写满 `tasks.md` 之前，列出所有**会改变对外行为**的分叉（两条以上都合理的做法），问用户选哪一条。包括但不限于：实例是否复用、是否把结果交还触发方、是否跳过现有初始化、进程外入口的每条到达路径如何处理。

- 接线细节（字段名、import、与现 API 同名的参数）不要拿来问用户
- 用户未选的分叉：写入 `schemes.md`「未决事项」（选项写清），**停止**，不要声称可 implement
- 用户选定后：写入「已决事项」，从「未决事项」删掉；**被否决的选项不要留在文件里**（省 token、防落实 Agent 再选一遍）
- 「未决事项」非空时：可以先落盘 `schemes.md` 供用户看，但不可把 `tasks.md` 当成已闭合合同，也不可提示去 **mode-implement**

### 3. 新建或修订目录

**新目标**：新建 `agents/proposes/<name>/`（`proposes` 不存在则先建）。同名目录已存在且目标不同，则换更具体的动词短语，不要覆盖。

**同一目标补全**：修订该目录内文件，不要另起同目标目录。

修订约束：

- 只增补或改写 `tasks.md` 里**未勾选**项；不改已 `[x]`
- 不改「目标」，除非用户要求改目标本身
- 「方案 / 已决事项 / 关注点」仅在用户改口或补拍板时更新，并同步未勾选任务

### 4. 写入 `schemes.md`

栏目名固定，不要增删或改名：

```
## 目标

<要达成什么；可数句，须可验收>

## 方案

<选定路径怎么做；可分条，只写已选定路径>

## 已决事项

- <用户拍板的选择；无则写「（无）」>

## 关注点

- <落实时易错的顺序、禁令、与现码的关系；不代替任务>

## 未决事项

- <尚未拍板的分叉与选项；闭合时必须为「（无）」>
```

约束：

- 「关注点」只写执行时要盯的约束；**凡是要改代码的，必须同时出现在 `tasks.md`**
- 不要标题以外的前言；不要大段实现代码。短列表、必要时一行示意可以
- 「方案」服务已决路径，不是备选百科

### 5. 写入 `tasks.md`

按落实顺序分成若干 **步骤**（大类）。栏目形态固定：

```
## 步骤 1：<短名>

- [ ] 在A文件中的F1函数中新增变量V1；
- [ ] 在B文件的F2函数中读取变量V1；

## 步骤 2：<短名>

- [ ] ……；
```

要求：

- 步骤标题：`## 步骤 N：` + 短名；N 从 1 连续
- 每项一句，以中文分号 `；` 结尾；新建时全部 `- [ ]`
- 写清：**哪个文件**、**哪个函数/位置**、**做什么**
- 后一步可以依赖前一步已引入的符号
- 不要在 `tasks.md` 写步骤以外的章节或代码块

### 6. 可落实性自检（闭合才可交付给 implement）

把两份文件当成无记忆执行器的输入。任一条失败就补任务或回到第 2 步问用户，不要用「方案」段落充数：

- **未决为空**：「未决事项」为「（无）」
- **已决可执行**：每条已决事项在 `tasks.md` 有对应落实项（或明确「不改代码」的关注点）
- **符号闭合**：新引入的函数 / 类型 / 通道，必须有任务写明接到**已有**调用点（生命周期、回调、路由、初始化）
- **到达路径**：进程外新入口的每一种到达（进程未起 / 已起 / 是否复用实例）各有任务
- **不变量进任务**：「方案 / 关注点」里会影响对错的禁令或分支，必须有对应 `- [ ]`

## 禁止

- 修改 `agents/proposes/` 以外的任何文件
- 按方案去改工程目录
- 用领域常识替用户做产品选择，或假定落实 Agent 会自己补分叉
- 未决非空时提示 **mode-implement**
- 把实现代码或长文备选方案堆进 `tasks.md`

## 用户要求修改工程目录时

提示使用 **mode-implement**。本模式不落地产品代码。未决非空时仍先拍板，不要把用户往落实上推。

## 交付

用中文告知：目录路径、`schemes.md` / `tasks.md` 是否闭合、步骤数与未勾选任务条数。

- 未决非空：只列出待选分叉，等用户；不要叫 implement
- 已闭合：提示使用 **mode-implement**
- 若为修订：说明改了哪些未勾选任务或已决事项
